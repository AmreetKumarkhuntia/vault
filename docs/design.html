Design & implementation plan

testkit — black-box API test harness

A Rust CLI that surrounds an untouched HTTP server with everything it needs to be tested: seeded Postgres & Redis, a recording mock for its external dependencies, YAML-defined test cases, and verification that tells you exactly which expected insertion or outbound call is missing.

1What it does & why

The system under test (the target) is a black box: an HTTP API server started separately, never modified. Its only coupling to the harness is configuration — its database DSNs point at the test stores, and its third-party base URLs point at testkit's embedded mock server.

Each requirement from the original brief maps to a first-class feature:

RequirementHow testkit handles it
Black-box serverTarget runs untouched; testkit only needs its base URL and a health endpoint.
Dynamic test driverThe CLI engine fires GET/POST/PUT/DELETE steps at the target per YAML definition, chaining captured values between steps.
Mocked external callsOne embedded HTTP listener impersonates every dependency (path-prefix per service), serves canned/sequenced responses, and records every request it receives.
Pre-seeded DB readsseed: blocks insert Postgres rows and Redis keys before each test, inside one transaction.
Verify missing insertionsverify.postgres: reports precisely which expected row is absent, with a per-column near-miss diff against the closest actual row.
Verify PUT/POST/DELETE the app makesverify.calls: matches the mock's recording log against expectations — missed calls, unexpected calls, wrong-body near-misses, and ordering.
One-by-one executionRun a single test by name, filter by tag/glob, or --step through a test interactively, inspecting DB, variables, and recorded calls at each pause.
Use previous test's dataFlows: ordered chains of tests in a *.flow.yaml — a stage exports its captures, later stages consume them as {{ flow.* }}, with the flow as the isolation unit.

2System overview & test lifecycle

                  ┌────────────────────────────────────────┐
 YAML suites ───▶ │              testkit (CLI)             │
                  │    dsl ─▶ core engine ─▶ report        │
                  └──────┬──────────┬───────────┬──────────┘
                  seeds/ │          │ steps     │ serves canned deps,
                  verify │          │ (reqwest) │ records every request
                         ▼          ▼           ▼
                   ┌──────────┐  ┌────────┐  ┌───────────┐
                   │ Postgres │  │ TARGET │─▶│ mock deps │
                   │  Redis   │◀─│  (black box HTTP srv) │
                   └──────────┘  └────────┴───────────────┘

Every test runs through a fixed state machine:

LOAD→ VALIDATE→ RESET→ SEED→ ARM MOCKS→ RUN STEPS→ VERIFY END-STATE→ REPORT→ CLEANUP
  • Validate everything before running anything. All YAML is parsed and cross-checked up front (unknown fields, dangling template references, undefined mock names). A bad suite aborts the whole run with exit 2 before a single test executes.
  • Reset before, not clean after. Isolation runs at the start of each test (TRUNCATE … RESTART IDENTITY CASCADE, FLUSHDB, clear mock state). A crashed run can never poison the next one, and failed-test state stays in place for post-mortem inspection.
  • Fail-fast between steps, collect-all within. A failed step stops the step sequence (later captures would be garbage), but all assertions inside a step are evaluated and reported together.
  • End-state verification always runs — even when a step failed. “The response was wrong and here's what actually hit the DB and mocks” is the debugging gold.
  • Run-level preflight probes the target's health endpoint, Postgres, Redis, and the mock listener before test #1; any failure exits 3 immediately with a reachability table instead of letting forty tests time out.
  • Serial in v1. One target and one database means one test at a time; the session abstractions reserve clean hooks for parallel lanes later.

3The YAML test language

Tests are pure data — no scripts, no Rust. That constraint is what lets the engine enumerate exactly what is missing when something fails.

File layout & global config

tests/
  testkit.yaml              # global config: environments, DSNs, mock bind, defaults
  fixtures/                 # shared seed/mock fragments, .sql files
  orders/
    _suite.yaml             # optional per-directory defaults (tags, shared seeds, timeouts)
    create_order.test.yaml  # one test per file

testkit.yaml holds environments (local, ci, …) with the target base URL + health check, Postgres/Redis URLs, and the mock bind address. Connection strings live only here — a test file can never silently point at production. Layering: CLI flags > TESTKIT_* env vars > testkit.yaml.

Anatomy of a test

A complete, realistic example — create an order, which charges a card through a mocked payment service, inserts a row, and warms a cache:

test: create order happy path
tags: [orders, smoke]

seed:
  postgres:
    - table: users
      rows: [{ id: 1, email: alice@example.com, status: active }]
    - table: wallets
      rows: [{ user_id: 1, balance_cents: 50000, currency: USD }]
  redis:
    - set: { key: "session:alice", value: tok_abc, ttl: 600 }

mocks:
  payments:                      # target's PAYMENTS_URL → {{ mock.payments.base_url }}
    unmatched: fail              # any request no stub matches → 599 + test fails
    stubs:
      - name: charge-ok
        match:  { method: POST, path: /v1/charges,
                  body: { json_partial: { currency: USD } } }
        response: { status: 201, json: { id: "ch_{{ uuid() }}", status: succeeded },
                    latency: 30ms }
  email:
    stubs:
      - name: send-ok
        match: { method: POST, path: /send }
        response: { status: 202 }

steps:
  - name: create
    request:
      method: POST
      path: /api/orders
      headers: { Authorization: Bearer tok_abc }
      json: { user_id: 1, items: [{ sku: SKU-BOOK, qty: 1, price_cents: 2500 }] }
    expect:
      status: 201
      json_partial: { status: pending, user_id: 1 }
    capture:
      order_id: { jsonpath: $.id }          # JSON-typed: a number stays a number

  - name: order visible
    request: { method: GET, path: "/api/orders/{{ order_id }}" }
    expect:  { status: 200, json_partial: { total_cents: 2500 } }
    repeat:  { every: 200ms, timeout: 5s }  # HTTP-level polling

verify:                            # end-state, evaluated after all steps
  postgres:
    - table: orders
      expect:
        - user_id: 1
          status: pending
          total_cents: 2500
          external_charge_id: { regex: "^ch_" }
          created_at: !near-now 10s   # tag matchers: !any !uuid !iso8601 !null …
      count: exact                    # extra rows in this key-space = failure
      eventually: 5s                  # bounded polling for async writers
    - table: wallets
      expect: [{ user_id: 1, balance_cents: 47500 }]
  redis:
    - key: "order:{{ order_id }}:summary"
      json_partial: { status: pending }
      ttl: { gt: 0 }
  calls:                           # what the TARGET sent to its dependencies
    - name: exactly one charge
      dependency: payments
      match: { method: POST, path: /v1/charges }
      body:  { json_partial: { amount_cents: 2500, order_ref: "{{ order_id }}" } }
      count: 1
    - name: confirmation email
      dependency: email
      match: { method: POST, path: /send }
      count: 1
  ordered: [[exactly one charge, confirmation email]]
  unexpected: fail               # unplanned traffic to mocked deps fails the test

Templating & reuse

  • minijinja, expressions only ({{ }}; logic blocks rejected in v1 — tests stay declarative). Namespaces: vars.*, steps.<name>.captures.* (plus flat shorthand), mock.<dep>.base_url, allow-listed env.*; builtins uuid(), now() (frozen per test so !near-now has a stable anchor), random_int().
  • Typing rule: a scalar that is exactly one expression substitutes the native JSON value — captured numbers stay numbers, which is what makes DB matchers work.
  • Reuse: YAML anchors, fixture: file includes for seeds/mocks, {$include: path, with: {…}} deep-merge, and _suite.yaml defaults. No test inheritance in v1.

Chaining tests: flows (use one test's data in the next)

Step captures chain data within a test. To reuse data across tests — the create-order test's order_id feeding the update and delete tests — an ordered chain of existing tests is declared in a *.flow.yaml file:

# tests/orders/lifecycle.flow.yaml
flow: order lifecycle
reset: once                  # the flow is the isolation unit: DB/Redis reset before stage 1 only
stages:
  - test: create order happy path
    export: [order_id]        # promote this test's captures into flow scope
  - test: update order
    with: { order_id: "{{ flow.order_id }}" }   # injected into that test's vars
  - test: delete order
    with: { order_id: "{{ flow.order_id }}" }
on_failure: skip-rest        # later stages report SKIPPED(dependency failed), never silent green
  • Tests stay independently runnable — they declare inputs as vars: with defaults (or required: true); with: overrides them, and nothing inside a test file knows about flows.
  • Exports are explicit and validated — a {{ flow.* }} reference no earlier stage exports is a static validation error, before anything runs. Values stay JSON-typed.
  • Per-stage mocks and verify — each stage arms its own mock session and recording buffer, so verify.calls never sees a previous stage's traffic.
  • CLI: testkit run 'order lifecycle' runs the chain; naming a mid-flow stage runs everything up to and including it. Flows shuffle as one atomic unit, and --step pauses across stage boundaries too.
  • Deferred: a free-form needs: dependency DAG — linear flows are deterministic and reportable, and a DAG can layer on later without breaking the DSL.

4Verification semantics

This is the product. Every failure is a structured object — kind, YAML path, expected value, near-misses with field-level diffs — rendered identically to the terminal and the JSON report.

Missing insertions, precisely

Expected rows drive targeted queries (no full-table snapshots by default). Literal columns become the SQL WHERE; matcher columns (!uuid, { gt: 0 }, regex…) check client-side. Actual rows are assigned to expectations — upgraded to proper bipartite matching when expectations overlap, so a greedy order can never produce a false negative. An unmatched expectation gets a ranked near-miss report:

✗ postgres: table `orders` — 1 of 2 expected rows MISSING  (after 5.0s, 24 attempts)
  closest actual row: id=482 — 3 of 4 columns match

  column        expected                     actual
  user_id       1                            1                        ✓
  status        confirmed                    pending                  ✗
  total_cents   4200                         4200                     ✓
  created_at    <within 5s of test start>   2026-09-23T10:14:02Z     ✓

“Row not found” is never the whole message — the report shows the closest candidate and exactly which column diverged.

Outbound-call verification

The mock records every request unconditionally (with a global sequence number), whether or not a stub matched. Verification is an assignment problem: each expectation absorbs between lo and hi recorded calls, each call counts at most once, lower bounds satisfied by bipartite matching. Leftover recordings to mocked dependencies are UNEXPECTED_CALL failures; unsatisfied expectations are MISSED_CALL failures with a weighted near-miss (“method ✓ path ✓ body ✗” plus a JSON diff). ordered: groups check sequence numbers. A dedupe: key collapses target retries before counting.

Eventual consistency: eventually: with settle semantics

Targets often write to the DB or call dependencies after responding. Any end-state assertion accepts eventually: 5s — a shared poll loop per verify block. Positive assertions pass on the first fully-successful poll. Negative assertions (absence, count: 0, no-unexpected-calls) must hold continuously for a settle window (default 500 ms) — an instantaneous “nothing arrived yet” proves nothing about in-flight async work.

Watch mode (opt-in)

watch: [orders, payments] snapshots PK + row-hash per table before steps and diffs after. Every observed insert/update/delete must be claimed by an expectation; unclaimed diffs fail as UNEXPECTED_CHANGE with before/after values. This is the “nothing else changed” guarantee, priced honestly at two scans per watched table.

Isolation strategy

Postgres

TRUNCATE t1, t2… RESTART IDENTITY CASCADE in one statement before each test. Table list from config or information_schema minus exclusions (migration tables). Fast, resets sequences, safe while the target holds pool connections.

Transaction-rollback isolation is impossible for a black-box target — it owns its own connections, so its writes can't be inside our transaction and our uncommitted seeds would be invisible to it. Documented loudly.

Redis

Dedicated logical DB (e.g. db 15) + FLUSHDB ASYNC. Preflight refuses db 0 without an explicit override flag. Prefix-SCAN deletion is the fallback for Redis Cluster.

testkit run --shuffle --seed N audits that tests really are order-independent.

The key extensibility trick — driver-owned documents

The YAML under seed.postgres: or verify.redis: is not parsed into a universal schema (none fits PG tables, Redis keys, and a future Mongo collection at once). The DSL keeps store blocks as raw values tagged by store kind; each driver deserializes and validates its own block. Adding MySQL later = one new crate + one registration line in the CLI. Nothing else changes.

The trait boundary the whole design hangs on:

// testkit-store — the leaf crate every driver implements
#[async_trait]
pub trait StateStore: Send + Sync {
    async fn ping(&self) -> Result<(), StoreError>;
    async fn reset(&self, spec: &ResetSpec) -> Result<(), StoreError>;
    async fn seed(&self, doc: &StoreDoc) -> Result<SeedReceipt, StoreError>;
    async fn snapshot(&self, doc: &StoreDoc) -> Result<Snapshot, StoreError>;  // watch mode
    // NEVER Err for a failed assertion — that's data in VerifyOutcome.
    // Err is reserved for harness faults (connection lost, type error).
    async fn verify(&self, doc: &StoreDoc, opts: &VerifyOpts) -> Result<VerifyOutcome, StoreError>;
    async fn inspect(&self, query: &str) -> Result<Table, StoreError>;         // step mode, read-only
}

Failure data is report-shaped from birth: CheckFailure { yaml_path, expected, kind, near_misses, attempts, elapsed } with kinds like MissingRow, UnexpectedCall, ValueMismatch { diffs }. The terminal renderer and the JSON report consume the same structs — the JSON report is lossless, never a re-parse of terminal text.

Mock internals: one axum listener for the whole run (the target reads its config once, so the address must be stable); N dependencies share it via path prefixes. Stubs match in declaration order, first full match wins — predictability over specificity scoring. Unmatched requests answer with status 599: unmistakable in target logs, impossible to confuse with a real upstream. Serving is deliberately separate from verification (canned-serve now, strict verify later against the recording log) — which is why this is bare axum and not wiremock.

6CLI & step-by-step mode

testkit run [PATTERN] [--tag t]… [--env name] [--step] [--break-at test:step]
            [--shuffle [--seed N]] [--report out.json] [--junit out.xml] [-v|-vv]
testkit list [PATTERN] [--tag t]     # resolved run plan, no execution
testkit validate [--live]            # static checks; --live dry-runs seeds, rolled back
testkit env [--env name]             # print mock/dependency URLs to export before starting target

Exit codes: 0 pass · 1 a test failed · 2 config/usage error · 3 environment/preflight error · 130 interrupted. CI dashboards can tell “broken tests” from “broken environment”.

--step pauses after seeding, after arming mocks, after every step, and before end-state verification:

CommandEffect
c / nContinue to next pause / advance one
respLast step's full request and response
varsVariable scope chain, including captures so far
calls [dep|seq]Mock recording log as a table, or one exchange in full detail
db <sql>Query Postgres inside BEGIN READ ONLY … ROLLBACK
redis <cmd>Allow-listed read-only Redis commands
verifyRun the verify block right now, non-destructively, single-shot
q / QAbort this test / abort the whole run

9Risks & decided defaults

RiskMitigation
YAML → PG type impedanceDriver caches information_schema column types and binds with explicit casts; validate --live dry-runs seeds in a rolled-back transaction; type errors name table, column, and YAML path.
Isolation leaksReset-before-test; settle quiesce before verify; unmatched: fail surfaces stray background calls; --shuffle audit. Target in-process caches don't reset with the DB — documented; a reset.script hook can hit a target reset endpoint if one exists.
Async flakiness vs speedeventually: + settle built into the verify options; failure reports carry the best observation across all polls, so even a flake report shows what was there.
Mock fidelity ceilingDeclaration-order matching is the documented rule; session-key hub reserves parallel/keyed routing; passthrough mode for hybrid setups.
Ecosystem driftYAML isolated behind one crate; diffing owned in-tree; versions pinned at the workspace root; version: 1 header in suite files.

Defaults chosen (revisit when needed)

  • Parallelism: serial v1; session abstractions keep parallel lanes open for v2.
  • Target startup: stays external; testkit env bridges the config gap (fixed mock port for CI). An optional target-launcher can come later.
  • Payloads: JSON + urlencoded + raw regex in v1; multipart/binary deferred.
  • gRPC / Kafka dependencies: out of scope for v1; the keyed schema (mocks.<name>) extends without breaking changes.
  • Parameterized tests: matrix: key reserved, feature deferred.
  • Secrets: env interpolation + configured-header redaction in reports.
